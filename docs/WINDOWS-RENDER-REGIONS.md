# Windows: чёрная область CEF после 0.2.6

Пользователь подтвердил, что 0.2.6 не исправила отрисовку. В актуальном журнале
есть созданные CefBrowserWindow/Chrome_RenderWidgetHostHWND и JavaScript страниц.
Причина чёрной области этим не установлена. `visible=false` в старой диагностике
не доказывает проблему показа: кнопка сначала скрывала все движки.
Старый engine.log от Chromium к CEF-сеансу не относится.

Добавлен обход возможного перекрытия страницы оболочкой WebView2: собственные
непосредственные дочерние HWND Tauri получают регион с вырезанной областью CEF.
При открытии диалога, закрытии последнего движка и отсутствии активного HWND
полная область возвращается. Изменения выполняются в UI-потоке; номер обновления
отбрасывает устаревшие задачи. CEF-процессы и их окна не получают этот регион.
Координаты переводятся через экран с учётом позиции дочернего HWND.
Регионы освобождаются через RAII, после успешного SetWindowRgn владение у Windows.
Повторная установка одинакового региона пропускается, чтобы не зациклить события.

Основание механизма: [SetWindowRgn](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowrgn)
ограничивает область, в которой окно может рисовать. Это обход определённого
класса перекрытий, а не доказательство корня пользовательского дефекта.

Диагностика теперь снимается ДО скрытия CEF. Добавлено полное дерево главного
окна, PID/поток/родитель, сосед выше по Z-order, exstyle и регион. Снимок до
диалога позволяет отличить невидимый контейнер от перекрытия живого CEF.

Добавлен Windows runtime-прогон `tests/gui/windows_render.py`: настоящий Tauri,
WebView2 через локальный CDP и CEF с локальной data-страницей. Проверяется реальный
экранный пиксель (24,85,65) после запуска, возврата из диагностики, resize и
сворачивания рейки. Тест сохраняет PNG/диагностику/JSON и падает при чёрном экране.
Профили изолированы через NEXUSBRO_TEST_DATA, WebView2 имеет отдельный каталог.
Нужен интерактивный Windows desktop; успешная компиляция не заменяет этот прогон.
Workflow сборки выполняет сценарий на Windows и сохраняет доказательства.

Локально: npm build, Linux cargo build и Windows GNU check с cef/dox прошли.
Windows-результат и проверку пользовательской машины учитывать отдельно.

Обновление выреза также привязано к `zadat_mesto`: CSS-resize панели может
не менять размер HWND. Команда выполняется асинхронно с сериализацией оконных
операций; при смерти движка область оболочки восстанавливается сторожем.
Windows-тест проверяет цвет у левого/правого краёв и в центре страницы.

Повторный Linux GUI и полный stress прошли: reopen 288–296 мс, edit 355 мс,
close 89–156 мс, max UI в stress 506 мс. Сохранены JSON в
[verification/windows-region](verification/windows-region/).

## Windows A/B по настоящим установщикам

Исходный 0.2.6, CI runtime 43411209856: локальная data-страница загрузилась,
в сессии заголовок RenderFixture и zagruzka=false, но экранные RGB у краёв
и в центре (17,19,26), то есть фон оболочки вместо страницы. Есть PNG и JSON
сессии в verification/windows-region/baseline-0.2.6/. В конце baseline-стенд
также поймал ошибку копирования занятой Cookies DB; её убрали, копируются
только журналы и JSON сессии. Это не отменяет более ранний pixel assertion.

Первый кандидат 94cf1b2, CI runtime 43410717720: RGB (24,85,65) во всех трёх
точках после старта, диалога и resize. После сворачивания рейки левая точка
показала фон оболочки — устаревший вырез. Это исправлено в ca2a1a3 привязкой
к zadat_mesto. Итоговый пакет 0.2.7 проверяется отдельно в CI 43411146104.
CDP WebView2 оказался недоступен (флаг отладки не появился в процессе), поэтому
приёмка переведена на tests/gui/windows_physical.py с PyAutoGUI и NEXUSBRO_PROBA=1.
