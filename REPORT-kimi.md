# Отчёт бенч-задачи: зависание супер-вкладок (Kimi)

Ветка: `bench/kimi-supertabs` (от `aa0dcd5`). Платформа проверки: Linux,
Xvfb (`:77`), реальные CEF-процессы. Лимит: 2 часа, уложился.

## 1. Воспроизвелось ли зависание

Да. Оба дефекта воспроизведены стабильно (4+ прогона подряд), не по
одному разу. Метод: двухпрогонный сценарий `NEXUSBRO_PROBA` под Xvfb.

- **PROBA=4** (прогон 1): создаёт супер-вкладки «proba» и «proba2»,
  приложение убивается (`KILL`), как user убивает зависшую программу.
- **PROBA=3** (прогон 2, после перезапуска): приложение поднимает
  активную вкладку само, затем сценарий проходит три жалобы по очереди:
  открытие уже созданной (спящей) → правка → удаление. Каждый шаг
  замеряется, между шагами зонд `run_on_main_thread` фиксирует, свободен
  ли UI-поток; границы команд пишутся в `zhurnal.log` на диске.

Воспроизведение требовало честной уборки между прогонами: `xvfb-run` +
`timeout` оставляют приложение сиротой (TERM уходит обёртке), а CEF-цикл
со сном 8 мс голодал следующий прогон — это артефакт стенда, в отчёте
отделён от багов приложения (свой Xvfb, KILL прямо в бинарь, pkill до
нуля между прогонами).

## 2. Корневая причина

Нашлось **два независимых дефекта**, каждый из которых даёт наблюдаемые
«подвисания». Тяжёлые команды вне UI-потока (0.2.3/0.2.4) уже были — их
я не трогал, они не виноваты.

**Дефект А — гонка сторожа окон (объясняет все три жалобы разом).**
Сторож раз в секунду снимает `(pid, окно)` каждой вкладки и потом до
секунды ищет окно (`najti_okno(pid, 1)`). Если за это время вкладку
перезапустили — а правка/перезагрузка делают ровно «kill старого +
spawn нового», — снимок устаревал, но проверки сходились: старый pid
мёртв, старое окно уничтожено (XID в это окно переиспользован новым
окном). Сторож глушил состояние **живого нового движка**: вкладка
«спит» при работающем процессе и лежащем поверх окне. Дальше по цепочке:
открытие такой вкладки спавнит второй процесс на тот же профиль →
«движок не ответил за 25 с» (подвисание при открытии); удаление не
находит процесс (`proc=None`) → не убивает его, стирание профиля ползёт
по ретраям при живом держателе файлов (подвисание при удалении);
повторная правка бьётся с двумя процессами (подвисание при правке).
В журнале дымовая связка: `запуск ок, окно N` → в ту же секунду
`движок умер, вкладка спит`. Поймано прогоном PROBA=3 четырежды.

**Дефект Б — PDEATHSIG убивала движок автостарта (Linux).**
`PR_SET_PDEATHSIG` привязана к потоку, а не к программе (та же грабля,
что 06.11.2026 со старым запускателем, и тот же урок в гайде: «все
движки запускает один долгоживущий поток»). В CEF-схеме этого не
сделали: `zapustit_cep` спавнил whoever-успел-первым. Потоки команд Tauri
живут достаточно, а служебный поток автостарта выходит сразу после
`spawn` — дочка получала SIGKILL раньше, чем напечатать `NB-OKNO`.
Картина в прогоне: процесса движка нет в `ps`, вкладка активной прошлого
сеанса через 25 с уходит в «движок не ответил» — активная вкладка мертва
при старте программы. Поймано 4 прогона подряд до фикса, 0 после.

## 3. Что изменено (коммиты)

- `f30d31b` — bench: сценарий самопроверки PROBA=3 (открытие/правка/
  удаление созданной ранее с замерами и зондами главного потока),
  PROBA=4 готовит состояние; граница «готово» у `zakryt` в журнале.
- `f95f3db` — **fix (дефект А)**: сторож перед усыплением сверяет, что
  в состоянии вкладки всё ещё тот же pid и то же окно и что запуск не
  идёт прямо сейчас; иначе записывает «снимок устарел, не трогаю».
- `9f97db5` — **fix (дефект Б)**: спавн CEF-детей ушёл в один
  долгоживущий поток `zapuskatel-cefa` (паттерн `brauzer::ZAPUSKATEL`),
  `zapustit_cep` ходит туда через канал с честным таймаутом; плюс
  `dozhdatsya_okna` различает молчание и мгновенную смерть дочки.

Каждый коммит компилируется (`cargo build` зелёный на каждом шаге).

## 4. Верификация критериев (доказательства)

Прогон верификации после обоих фиксов (полный журнал и stdout — ниже,
файлы сохранены на машине стенда):

- **Открытие созданной ранее — без фриза (<1 с)**: команда
  `pereklyuchit` — 0.004 с; окно движка в журнале через ~1 с
  (`:403 pereklyuchit(proba): вход` → `:403 proba: запуск ок`).
- **Удаление — без фриза**: `zakryt` целиком 1.005 с, включая остановку
  процесса и стирание профиля; в журнале `:405 …остановлен → готово`.
- **Правка — без фриза**: `izmenit` 1.023 с (kill + respawn; окно нового
  движка в ту же секунду).
- **Создание и переключение работают**: прогон 1 — оба `otkryt ok=true`,
  `запуск ок` через 1–2 с.
- **UI-поток свободен на всех путях**: зонды `run_on_main_thread`
  0.000–0.001 с между каждыми шагами (до фиксов те же зонды 0.000 —
  фриза UI-потока не было и до; тормозили дети/состояние, не интерфейс).
- **Приложение собирается**: `cargo build` — Finished, 0 errors
  (проверялось после каждого коммита; сборка с `CEF_PATH`, dev-билд
  278 МБ).
- **Проверено реальным запуском**: 5 полных двухпрогонных циклов под
  Xvfb с реальными процессами CEF (деревья zygote в `ps`), не «должно
  работать».

Ключевые фрагменты доказательств (последний прогон, после фиксов):

```
Журнал (zhurnal.log):
:371 proba2: запуск ок, окно 18874370        ← прогон 1
:401 proba2: запуск ок, окно 8388610         ← АВТОСТАРТ раньше: «не ответил за 25 с»
:403 pereklyuchit(proba): вход
:403 proba: запуск ок, окно 16777218         ← открытие созданной ранее
:404 proba: запуск ок, окно 16777218         ← перезапуск после правки
:404 proba: движок умер, вкладка спит        ← сторож про старый pid
:404 proba: снимок сторожа устарел, вкладку не трогаю   ← ФИКС А
:405 zakryt(proba): остановлен → готово
:405 zakryt(proba2): остановлен → готово

Сценарий (stdout, секунды от старта потока):

До фиксов (4 прогона подряд, идентичные симптомы):

```
:XXX proba2: движок не ответил за 25 с       ← автостарт мёртв, процесса нет в ps
:XXX proba: запуск ок, окно 8388610          ← перезапуск при правке

ожидание автостарта: 30.004 с                ← сценарий ждал окна впустую

Не воспроизвёлось на стенде (честно): сами заметные многосекундные
фризы интерфейса из жалобы — на Linux UI-поток оставался свободен
(зонды ~0). Замедления были «вечное Запускаю…» и мёртвые/потерянные
вкладки. Риск для Windows, где блокировки держат файлы профиля:
`steret_profil` после убийства может ползти по ретраям — на Linux не
проявилось (первый `remove_dir_all` прошёл).
