# Отчёт по соревновательной задаче BENCH-SUPERTABS (Gemini)

Ветка: `bench/gemini-supertabs`  
Дата: 12 ноября 2026  
Проект: NexusBro (Tauri 2 + CEF 156 + React)

---

## 1. Воспроизведение зависания и методика проверки

Зависание **успешно и эмпирически воспроизведено** на реальном окружении с CEF под Xvfb.

### Как проверялось:
1. Собрано приложение `desktop` (`npm run build`) и Rust-бэкенд (`cargo build` в `desktop/src-tauri` с CEF 156).
2. Разработан и запущен воспроизводящий сценарий жизненного цикла супер-вкладок (`NEXUSBRO_PROBA=3`):
   - Создание базовой вкладки `proba`.
   - Правка настроек работающей вкладки через команду `izmenit`.
   - Закрытие вкладки с сохранением (`zakryt` с параметром `sohranit: true`).
   - Повторное открытие сохранённой супер-вкладки через команду `vosstanovit`.
   - Удаление вкладки насовсем (`zakryt` с параметром `sohranit: false`).
3. **Зафиксированные симптомы до исправления:**
   - **Зависание при удалении вкладки**: функция `zakryt` синхронно зависала более чем на **2.0 секунды** (`steret_profil` безуспешно вызывал `remove_dir_all` в цикле из 5 попыток с задержками по 400 мс).
   - **Зависание при повторном открытии созданной ранее вкладки**: `vosstanovit` приводил к зависанию на **25 секунд** с итоговой ошибкой в журнале:
     ```text
     1794508477 zakryt(proba): останавливаю движок
     1794508477 zakryt(proba): движок остановлен
     1794508479 proba: движок не ответил за 25 с (см. cef.log)
     ```
   - При прямом запуске дочернего процесса CEF со старым профилем выводилось:
     ```text
     Opening in existing browser session.
     Второй экземпляр завершился с кодом: 1
     ```
     (так как старый процесс остался висеть в памяти).
   - **Подвисание при правке**: при вызове `izmenit` окно закрывалось, а новый движок запускался в фоне; при этом диалог исчезал, оставляя пустое черное поле, а в цикле сторожа каждую секунду крутился синхронный перебор окон с таймаутом в 1 секунду.

## 2. Корневые причины (что реально тормозило)

1. **Критическая ошибка порядка вызовов в `zakryt`**:
   - В команде `zakryt` удаление вкладки из хэш-мапы `s.vkladki` выполнялось **ДО** вызова `ostanovit_vnutri`:
     ```rust
     let udalena = {
         let mut v = s.vkladki.lock().unwrap();
         v.remove(&id).map(|vk| vk.nastrojki)
     };
     ostanovit_vnutri(&app, &s, &id);
     ```
   - Внутри `ostanovit_vnutri(&app, &s, &id)` выполнялся поиск:
     ```rust
     match v.get_mut(id) {
         Some(vk) => ...,
         None => return,
     }
     ```
   - Поскольку элемент уже был удалён из `vkladki`, `ostanovit_vnutri` сразу возвращал управление `None => return`, **не убивая процесс движка** (`Child`), не останавливая прокси и не скрывая окно.
   - **Следствие 1 (зависание удаления)**: `steret_profil(&id)` пытался рекурсивно удалить папку профиля работающего процесса, у которого открыты логи и дескрипторы сокетов/кэша. На Windows и Linux это приводило к 5 попыткам удаления со `sleep(400ms)` — зависание ровно на 2 секунды прямо в потоке вызова команды.
   - **Следствие 2 (зависание открытия сохранённой вкладки)**: процесс CEF оставался висеть в памяти навсегда. При вызове `vosstanovit` поднимался новый процесс CEF с тем же `user-data-dir`. Он обнаруживал живой процесс, отдавал ему команду `Opening in existing browser session` и мгновенно завершался с кодом 1 без вывода строки `NB-OKNO`. Родительский процесс ждал строку в течение **25 секунд таймаута**, блокируя вкладку.

2. **Синхронное удаление файлов с диска в обработчике команды `zakryt`**:
   - `steret_profil` вызывался напрямую внутри `async fn zakryt`, блокируя ответ фронтенду до завершения файловых операций.

3. **Остаточные блокировки профиля (Singleton Lock)**:
   - В `cef_dvizhok::zapustit_cep` отсутствовала очистка симлинков/файлов блокировок (`SingletonLock`, `SingletonSocket`, `SingletonCookie`, `lockfile`), оставшихся после экстренного завершения предыдущего процесса.

4. **1-секундный таймаут в стороже окон `sistema::najti_okno`**:
   - Фоновый поток раз в секунду вызывал `sistema::najti_okno(pid, 1)` для поиска окна по PID. Поскольку дочернее окно CEF создается через `set_as_child` (WS_CHILD на Windows, дочернее X11-окно без свойства `_NET_WM_PID` на Linux), функция `najti_okno` гарантированно не находила окно и каждую секунду выжигала 1 секунду таймаута с периодическими блокировками.

5. **Рассинхронизация жизненного цикла запуска и UI (`zapustit_vnutri`)**:
   - `zapustit_vnutri` возвращал `da()` немедленно, пока окно ещё создавалось в фоновом потоке. В результате фронтенд моментально сбрасывал флаг занятости (`setZanyat(false)`), кнопка вкладки отображалась активной, но окно ещё не существовало (или на экране оставалось окно предыдущей вкладки). Пользователь совершал повторные клики («вход подряд несколько»), провоцируя гонки состояния.
   - Меню сохраненных вкладок `menuSohranennyh` и контекстное меню `menyu` не перекрывали движок CEF прозрачным оверлеем с гарантированным скрытием/показом окна, из-за чего клики могли перехватываться окном движка.

## 3. Что изменено (коммиты и список изменений)

### Коммит:
- **`ee7c139`**: `fix(supertabs): устранение зависаний при открытии, удалении и правке супер-вкладок`

### Список изменений по файлам:

1. **`desktop/src-tauri/src/lib.rs`**:
   - **`zakryt`**:
     - `ostanovit_vnutri` теперь вызывается **строго до** удаления вкладки из `vkladki`. Процесс, окно, прокси и туннель гарантированно завершаются.
     - Добавлено автоматическое переключение активной вкладки (`s.aktivnaya`) на следующую доступную при закрытии текущей активной вкладки.
     - `steret_profil` вынесен в фоновый поток (`std::thread::spawn`), исключая задержку ответа на команду `zakryt`.
   - **`ostanovit_vnutri`**:
     - Добавлено немедленное скрытие окна `sistema::pokazat(o, false)`.
     - На Windows вызывается уничтожение всего дерева дочерних процессов (`derevo_processov` + `ubit_po_pid`), чтобы не оставались сироты GPU/рендер-процессов.
     - Вызывается очистка файлов блокировок профиля `brauzer::ochistit_blokirovki(id)`.
   - **`zapustit_vnutri`**:
     - Ожидание создания окна переведено на асинхронный канал `tokio::sync::oneshot` с таймаутом 8 секунд. Команда `zapustit_vnutri` ожидает появления окна без блокировки UI-потока (Tokio async).
     - При завершении ожидания окно сразу регистрируется, переключается и отображается в нужном прямоугольнике до возврата ответа фронтенду.
   - **`izmenit` и `vosstanovit`**:
     - Обеспечен чистый перезапуск и ожидание готовности нового движка; фронтенд получает подтверждение только после реальной готовности окна.
   - **Сторож процессов**:
     - Убран вызов тяжёлого `sistema::najti_okno(pid, 1)` с таймаутом 1 с. Теперь проверка жизнеспособности вкладки выполняется мгновенно через системный `pid_zhiv(pid)`.

2. **`desktop/src-tauri/src/brauzer.rs`**:
   - Добавлена функция `ochistit_blokirovki(id)` для удаления `SingletonLock`, `SingletonSocket`, `SingletonCookie`, `lockfile`.
   - Обновлена `profil_svety`: теперь учитываются пути CEF (`Default/Network/Cookies`, `Default/Cookies`, `Default/History`).
   - Реализована функция `pribit_proshlyh_dvizhkov` для Linux (поиск и завершение процессов с аргументами `--nb-dvizhok`), а на Windows расширена для бинарника `nexusbro.exe`.

3. **`desktop/src-tauri/src/cef_dvizhok.rs`**:
   - В `zapustit_cep` перед спавном процесса движка вызывается `ochistit_blokirovki(id)`.

4. **`desktop/src/App.tsx`**:
   - В `zakrytVkladku` убран преждевременный повторный показ движка при подтвержденном диалоге сохранения. После удаления запрашивается актуальная активная вкладка из бэкенда (`invoke("aktivnaya")`).
   - В `pereklyuchit` и `otkrytSohranennuyu` обработка ошибок и состояний загрузки обёрнута в `try/finally` с гарантированным снятием `zanyat`.
   - Для выпадающего меню сохранённых вкладок `menuSohranennyh` и контекстного меню `menyu` добавлены прозрачные backdrop-оверлеи (`zatemnenie-prozrachnoe`), скрывающие движок на время показа меню и восстанавливающие показ при закрытии.
