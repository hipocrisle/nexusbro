# Супер-вкладки: воспроизведение, исправление и проверка

## 1. Воспроизведение

**Воспроизведено реальными действиями в собранном desktop-приложении под Xvfb.** Исходный `NEXUSBRO_PROBA=2` успешно создавал и удалял две вкладки, но пользовательский GUI-сценарий он не покрывал.

Работа выполнена в `bench/codex-supertabs`. Начальное состояние — `d5dd0a5`, отчёт предыдущей попытки поверх исходного кода `aa0dcd5`. Перед работой прочитаны руководство проекта и карточка. Код приложения изменён только после воспроизведения. Лимит двух часов соблюдён.

Последовательность воспроизведения: создать вкладку → открыть ранее созданную → изменить настройки → закрыть с сохранением → нажать «+» или меню сохранённых вкладок. После закрытия нажатия переставали доходить до управления приложением. В журнале последним оставалось «движок остановлен».

Это была **блокировка кликов интерфейсным слоем**, а не доказанный дедлок Rust: после ответа «Сохранить» React сохранял `vopros`, слой `.zatemnenie` продолжал закрывать всё окно. Проверка `document.elementFromPoint(22,797)` вернула этот слой вместо кнопки «+». Доказательства: [DOM](bench-artifacts/baseline-overlay-proof.json), [снимок](bench-artifacts/dom-freeze.png), [журнал исходного прогона](bench-artifacts/baseline-commands.txt), [сборка исходной версии](bench-artifacts/cargo-build-baseline.txt).

После получения работающего нативного контента отдельно воспроизведена недоступность пункта «Настройки» **физическим кликом xdotool**: CEF перекрывал правую часть контекстного меню, и клик получала страница. Аналогичная проблема была у меню сохранённых вкладок. [Снимок перекрытия](bench-artifacts/menu-covered.png), [DOM меню](bench-artifacts/menu-covered-proof.json).

## 2. Причины и изменения

- **Незавершённый диалог.** Все ответы, включая отмену и клик по фону, теперь очищают `vopros` перед разрешением Promise.
- **Меню под нативным CEF.** Перед открытием контекстного меню и списка сохранённых вкладок движки скрываются. Отмена, выбор пункта и завершение операции восстанавливают активный движок. Новое окно, появившееся во время диалога, также учитывает состояние скрытия.
- **Удаление не останавливало движок.** `v.remove(...).map(|vk| vk.nastrojki)` выбрасывал `Child`, который сам процесс не завершает. Следующий `ostanovit_vnutri` уже не находил вкладку, но журнал сообщал об остановке. При GUI-проверке процесс удалённой вкладки действительно продолжал жить. Теперь удаление сохраняет владение ресурсами и завершает их вне UI-потока и мьютекса списка.
- **Гонки запуска с удалением и правкой.** `Child` сохраняется сразу после spawn. Каждый запуск имеет свой номер; старый ответ `NB-OKNO` не может воскресить удалённую вкладку или заменить новый движок. Ожидающий запуск также считается работающим при правке. Поздно запустившаяся вкладка не перехватывает выбор пользователя.
- **Профиль появлялся после удаления во время запуска.** Стресс-прогон обнаружил запись оставшимся подпроцессом CEF. На Linux каждый движок теперь запускается в отдельной группе процессов; перед удалением профиля завершается вся группа.
- **Синхронная очистка сохранённого профиля.** Перенесена в `spawn_blocking`; отсутствие каталога больше не вызывает пять задержек по 400 мс.
- **Оконные операции.** Вызовы показа и перемещения выполняются после снятия мьютекса списка. На Windows используются `ShowWindowAsync` и `SWP_ASYNCWINDOWPOS`, чтобы не ждать чужую очередь сообщений. Это защитное изменение; Windows-дедлок в данном Linux-прогоне не воспроизводился.
- **Два препятствия полноценной X11-проверке.** Трассировка доказала `BadMatch` при создании CEF с visual `0x21` и наследуемым colormap GTK visual `0x3b7`: [трасса](bench-artifacts/x11-badmatch.txt). Добавлен дочерний контейнер с совместимым visual/colormap и передачей размеров CEF. Для показа, скрытия и перемещения X11 теперь ожидается подтверждение запроса: одного `flush` перед закрытием соединения было недостаточно. Проверено по живому окну и странице, а не только `NB-OKNO`.
- CEF использует существующий долгоживущий поток запуска, необходимый для корректного `PR_SET_PDEATHSIG`. После закрытия активной вкладки ядро выбирает следующую; фронтенд получает действительное активное состояние вместо ID удалённой вкладки.

Коммиты исправлений — каждый после успешной сборки:

| Коммит | Изменение |
|---|---|
| `ff288ea` | Диалог, владение ресурсами, отмена старых запусков, совместимый контейнер X11, асинхронные оконные вызовы Windows |
| `6bd6d22` | Подтверждение показа и размера X11 |
| `bbf9042` | Завершение группы CEF перед удалением профиля Linux |
| `a7d5ebe` | Скрытие CEF под обоими меню |
| `6811460` | Асинхронное скрытие дополнительных окон и восстановление Windows |

## 3. Проверка критериев

Проверялись настоящие CEF-процессы и профили, React-интерфейс, команды Tauri и нативное дерево X11. Сеть — прямое соединение, страницы локальные `data:`. Автоматизация не подменяет backend или движок. Скрипт проверяет, что у контейнера есть дочернее окно CEF, активное окно действительно видно, а скрытые окна не отображаются.

Итоговый прогон: [скрипт](bench-artifacts/gui-supertabs.py), [все результаты](bench-artifacts/gui-acceptance-results.json), [замеры](bench-artifacts/gui-acceptance-results.txt), [журнал](bench-artifacts/acceptance-commands.txt).

| Критерий | Итоговый результат |
|---|---|
| Открытие ранее созданной вкладки <1 с | **Да:** 296–608 мс, четыре открытия сохранённого профиля; ожидалось появление готового нативного окна |
| Удаление без фриза | **Да:** 93–156 мс; после закрытия последнего движка живых процессов супер-вкладок нет |
| Правка без фриза | **Да:** 356 мс до нового готового движка, имя и настройки сохранены |
| Создание и переключение | **Да:** холодное создание 1144 мс до готового CEF, второй вкладки — 356 мс; переключения 92–96 мс |
| `cargo build` | **Да:** CEF 156.0.26, cef-rs 156.4.0, 18 предупреждений, ошибок нет — [протокол](bench-artifacts/cargo-build-release-candidate.txt) |
| Frontend | **Да:** TypeScript и Vite — [протокол](bench-artifacts/frontend-build-final.txt) |

Холодное создание нового профиля не укладывалось в секунду во всех прогонах; это время инициализации CEF, а не зависание интерфейса. Ограничение <1 с для открытия существующих вкладок выполнено. Таймер интерфейса с периодом 20 мс показал максимум 500 мс за весь итоговый стресс-прогон, включая 20 одновременных переключений; в отдельном обычном GUI-прогоне — 44 мс.

Дополнительные проверки итогового кода:

- Пять удалений во время запуска с искусственно остановленным через `SIGSTOP` CEF: 86–93 мс, основной PID прибран, профиль удалён и не появляется вновь.
- Правка вкладки с остановленным CEF во время запуска: старый PID завершён, остался ровно один новый движок.
- 20 одновременных переключений на запускающуюся вкладку: один процесс; после выбора другой вкладки поздний запуск её не перекрывает.
- Удаление сохранённой вкладки с уже отсутствующим каталогом профиля: менее 100 мс.
- Отмена вопроса, клик по фону, сохранение и удаление без сохранения: слой вопроса убран; соседний движок остаётся работоспособным.
- Перезапуск приложения восстановил активную вкладку за 204 мс после события фокуса. Движок оставался жив после завершения запускающего задания; контейнер и CEF изменили размер вместе с главным окном. Штатный выход — код 0, живых процессов профиля после него нет. [Результат](bench-artifacts/autorestore-results.json), [дерево после resize](bench-artifacts/autorestore-tree.txt), [скрипт](bench-artifacts/autorestore.py).

### Повторение

CEF-дистрибутив для сборки находится в игнорируемом `desktop/src-tauri/cef/`. Бинарные файлы движка и тестовые профили в коммиты не включены.

```bash
(cd desktop && npm run build)
(cd desktop/src-tauri && CEF_PATH="$PWD/cef" CARGO_BUILD_JOBS=2 cargo build)
Xvfb :92 -screen 0 1280x900x24 -nolisten tcp
```

В другом терминале, из корня репозитория, с новым изолированным каталогом данных:

```bash
DISPLAY=:92 WEBKIT_INSPECTOR_HTTP_SERVER=127.0.0.1:9223 \
  CEF_PATH="$PWD/desktop/src-tauri/cef" \
  XDG_DATA_HOME="$PWD/bench-artifacts/acceptance-data" \
  XDG_CONFIG_HOME="$PWD/bench-artifacts/acceptance-config" \
  XDG_CACHE_HOME="$PWD/bench-artifacts/acceptance-cache" \
  WEBKIT_DISABLE_SANDBOX_THIS_IS_DANGEROUS=1 \
  desktop/src-tauri/target/debug/nexusbro
```

Затем `python3 bench-artifacts/gui-supertabs.py --data bench-artifacts/acceptance-data --stress`. Нужен пакет Python `websocket-client`; при другом ID WebKit target используется `--target`. Скрипт ожидает изначально пустой тестовый список вкладок. Для физической проверки — `python3 bench-artifacts/physical-demo.py`. После штатного выхода `python3 bench-artifacts/autorestore.py` проверяет повторный запуск того же профиля.

## 4. Границы результата

Полноценный GUI-прогон выполнен на Linux/X11. Пользовательская Windows-машина и Wine не использовались; отсутствие Windows-специфических зависаний этим отчётом не утверждается. Windows-ветки успешно прошли проверку типов: `CC_x86_64_pc_windows_gnu=x86_64-w64-mingw32-gcc CARGO_BUILD_JOBS=2 cargo check --offline --target x86_64-pc-windows-gnu --features cef/dox` — [протокол](bench-artifacts/windows-check.txt). Флаг `cef/dox` отключает сборку и линковку нативного CEF, поэтому это проверка Rust/Windows API, а не Windows-бинарник или GUI-прогон. VPN и удалённые подписки в эти замеры не входят.
